# 登录验证码加载顺序修复验收

旧页面的验证码img没有src，要等 `layui.use` 加载pearAdmin后才设置地址。该依赖继续引入菜单、标签页等后台模块；整套pear.css也加载大量登录页无关样式。因此两种存储模式均可能出现页面已显示、验证码仍等待资源的问题。排查时源站直连验证码约19毫秒，服务器直连约44毫秒；这些是单次排查样本，不是压力测试或公网延迟承诺。

初始验证码改由HTML中的随机版本URL直接请求，不等待JavaScript。原生点击与Enter/空格刷新独立绑定；初始化不再重复请求验证码，失败登录会重新获取。登录页只加载必要的Layui、按钮及页面样式，模块缩减为form和layer。验证码仍使用既有会话和认证链路，响应增加private/no-store缓存控制。

本机在项目外 `/private/tmp/cms-captcha-load-20261111` 使用PHP多进程夹具：实际登录模板和资源，模拟主脚本延迟2秒、后台模块延迟2.5秒，以DEMO图片和固定成功/失败响应测试前端，不验证真实账号或验证码、不写业务数据库或用户Redis。夹具计时显示旧版验证码首次出现4642毫秒，新版9毫秒；该计时起点为夹具头部脚本执行，不能当作公网打开页面的耗时。新版初始图片仅加载一次，在主脚本完成前已可显示。浏览器通过鼠标与键盘刷新、失败后换图及恢复按钮、无结果dialog、成功轻提示及自动跳转回归，无原生离开确认或夹具控制台错误；截图包括before.png、after.png和live-after.png。

两份改动PHP文件语法、改动空白检查及2,132个实体的资源校验通过。公开资源字节、清单、源归档及恢复包未改动，继续使用revision `2026-11-11-feedback-style-v6`。8787准确目标完整重启，实际验证码返回120×40 JPEG及no-store；未操作8793。
